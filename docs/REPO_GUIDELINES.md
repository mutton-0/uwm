# Sky Lab 代码仓库规范

这份文档写给要把自己项目放进 `sky-lab-uw` 组织的同学看。目的很简单:别人(包括半年后的你自己,包括换一台机器、换一台车的你)拿到这个仓库,不用问你就能跑起来、看懂在干什么,也能信得过里面报的结果。

不需要写得多花哨,但下面几条是硬性要求,建组织的时候会照这个检查。

配套的两份文档:代码怎么合进 main,见 [MERGE_WORKFLOW.md](MERGE_WORKFLOW.md);提 PR 前逐项自查,用 [REPO_CHECKLIST.md](REPO_CHECKLIST.md)。

## 一、仓库里必须有什么

```
your-project/
├── README.md              必须,见下面的写法
├── requirements.txt        或 environment.yml / pyproject.toml,总之依赖要能装
├── configs/                参数、标定文件、超参配置
├── scripts/                跑起来用的脚本(train.sh, run_calib.py ...)
├── src/  或  <project>/     代码本体
├── data/                    只放小样例或 README 说明去哪下载数据,别传数据集
├── checkpoints/ 或 outputs/ 同上,只放 .gitignore,不传权重和日志
├── .gitignore
└── LICENSE                  没有的话默认按组内 MIT,问导师
```

不强制这个目录名一定叫 `src`,你原来的项目结构能看懂就行,但"代码、脚本、配置"这几类东西要能一眼分清楚,不能全堆在根目录一坨 `.py` 文件里。

## 二、README 写什么

README 只回答四件事:这是什么、怎么装、怎么跑、跑出来该长什么样。按这个顺序写,不用写成论文。"怎么跑"里至少要有一条能直接复制粘贴执行的命令,不是让人照着文字自己拼。

模板:

```markdown
# 项目名

一句话说这是干什么的,给谁用的。

维护人: @你的github用户名
状态: active / archived / 交接中

## 这是什么

2-4 句话说清楚背景和这个仓库解决的问题。如果依赖其他仓库(比如标定结果要喂给 vla 那个仓),在这里说清楚上下游关系。

## 环境

- Python 3.10 / ROS2 Humble / CUDA 12.1(按实际写,不要写"最新版本"这种)
- GPU: 型号、显存、驱动版本(比如 A6000 48G、驱动 555.42.06)—— 换机器第一步就是对比这张表,别等报错了才去猜
- 依赖: `pip install -r requirements.txt`
- 硬件依赖(如果有): 哪个相机型号、哪个机械臂,固件/驱动版本;涉及实车/实体机器人实验的,见下面"硬件与车辆实验"一节,这里只写软件能看到的部分

## 怎么跑

给能直接复制粘贴执行的命令,不要写"运行主程序即可"这种。

    python scripts/run_calib.py --config configs/d435i.yaml

跑完应该看到什么(输出文件、终端打印、图),截图或贴一段示例输出。

如果流程要开多个终端,写清楚哪几个要同时开着(并行)、哪几个必须等上一步跑完再跑(串行)。并行的部分重点标出来,比如:

    终端 A: 常驻跑数据/模型服务,不能关
    终端 B: 和 A 同时开,跑训练脚本;A 一关 B 就会报连接错误

## 结果

报了关键数字的项目加这一节:数字是怎么跑出来的、能不能复现、不能完全复现的话波动有多大、为什么。具体要求见下面"结果要能复现"一节。

## 数据 / 权重

数据集/预训练权重放在哪(NAS 路径、下载链接),不要指望别人问你要。演示视频/录屏同理,放网盘链接,不要把视频文件传进仓库。

## 已知问题 / TODO

写实话。有坑就说是什么坑,免得下一个人重踩一遍。
```

举个例子,相机标定的仓库大概长这样:

```markdown
# camera-calibration

RealSense D435i 与机械臂末端的手眼标定流程。

维护人: @boyue
状态: active

## 这是什么

用于标定相机坐标系到机械臂末端坐标系的变换矩阵,标定结果给 arm-setup 仓库里的抓取流程用。

## 环境

- Python 3.10, OpenCV 4.9
- GPU: 不需要,CPU 即可
- RealSense SDK (pyrealsense2==2.55.1)
- pip install -r requirements.txt

## 怎么跑

1. 采集标定板图像:
       python scripts/capture.py --output data/calib_0930/
2. 计算标定结果:
       python scripts/run_calib.py --input data/calib_0930/ --output configs/extrinsics.yaml
   跑完会在 configs/ 下生成 extrinsics.yaml,里面是 4x4 变换矩阵。

## 数据 / 权重

标定板图像不上传,示例数据在组内 NAS: /data/sky-lab/camera-calib-samples/

## 已知问题

- D435i 在近距离(<0.3m)畸变较大,标定板别放太近
- 目前只支持棋盘格标定板,ChArUco 还没接
```

这个例子不用照抄,但风格照抄:具体命令、具体路径、具体版本号,别写模糊的话。

## 三、命名和分支

- repo 名:`方向-内容`,小写加短横线,比如 `camera-calibration`、`vla-finetune`,不要把人名放进 repo 名。
- `main`:受保护,每月组会上 Owner 审批后合入一次,流程见 [MERGE_WORKFLOW.md](MERGE_WORKFLOW.md)。
- `monthly/YYYY-MM`:manager 维护的本月整合分支,成员的改动先通过 PR 合到这里。
- 自己开发用 `dev/你的名字` 或 `feature/具体描述`,比如 `dev/boyue`、`feature/charuco-support`。
- tag:每次月度合入后打 `base-YYYY-MM`;阶段性成果打 `v0.1`,投论文对应的版本打 `icra26-submission`。别把版本号写进分支名(`camera/boyue/v1` 这种不要)。

## 四、绝对不能提交的东西

- 数据集、模型权重、rosbag、日志、图片压缩包、视频文件 —— 这些体积大,进了 git 历史删不干净,统一走 NAS / HuggingFace / 对象存储 / 网盘,仓库里只放路径、下载脚本或链接。
- API key、内网 IP、账号密码、实验室 wifi 密码 —— 写进 `.env`,加进 `.gitignore`,不要写死在代码里。
- 大文件如果确实要进 git,用 Git LFS,先问一下额度够不够。

提交前养成习惯看一眼 `git status` 和 `git diff --stat`,别一把梭 `git add .`。

## 五、换一台机器要能跑起来

这是前面几条规则的终极目的,单独拎出来说清楚:

- 环境文件要带硬件信息。requirements.txt / environment.yml 旁边(或者 README 的"环境"段落)要写清楚 GPU 型号、显存、驱动版本、CUDA 版本,以及要求特定架构的依赖(比如某些 flash-attn 版本在新卡上装不上)。换机器拿到仓库的第一件事就是对比这张表,不是跑出一堆报错以后再去猜哪里不对。
- 代码里不要写死本机的绝对路径。做不到的话(共享机器、固定挂载盘这种情况下确实绕不开),必须在 README 里显式列出"这几个路径是本机专属,换机器要改",不能让它们悄悄埋在脚本参数默认值里。反面例子就在组里:`sim2real_demo_ttc` 这个分支的模型环境路径直接写死成类似 `/home/mut0/.conda/envs/simscale`、`/data/ruolin/envs/simlingo` 这种,换一个人、换一台机器,代码一个字不改,但这些路径对不上就全跑不通——不是不能写死,是写死了必须在 README 里标出来"照抄之前先查这几行",不能让人跑出 `FileNotFoundError` 才发现。
- 多终端/多进程的流程要讲清楚执行顺序,见上面 README 模板"怎么跑"里的写法。

## 六、结果要能复现

- 报告/论文里引用的关键数字,别人照着 README 跑一遍脚本应该能对上(合理误差范围内)。环境、种子、硬件都对,结果却对不上,这事比"跑不起来"更隐蔽也更麻烦,一定要在 README 的"结果"一节里说清楚。
- 做不到完全复现的,两件事都要写:
  1. **波动有多大**——跑多次给出分布(箱线图,或者均值±标准差/置信区间都行),不要只报一个单点数字当作"就是这个数"。
  2. **波动从哪来**——随机种子没固定、依赖某块 GPU 的浮点运算顺序、还是现场实验本身带的物理随机性(光照、路况、电量),原因要具体,别用"结果可能有波动"这种话糊弄过去。
- 涉及随机性的实验,README 的运行示例要带上固定种子的方法(比如 `--seed 42`),至少在能控制的范围内保证"同样输入跑出同样输出"。
- 实车/实地实验天然有一次性、不可逆的成分(路况、天气、电量),要单独说明这组数据是一次性采集还是可以复测、复测条件是什么,不能让人默认它跟仿真一样点一下就能重跑。

## 七、硬件与车辆实验

涉及实车/实体机器人实验的仓库,"硬件依赖"这项要比纯软件仓库写得更具体——装错一个线材、摆错一个角度,一整轮数据可能直接作废:

- **传感器的物理摆放**:摄像头/雷达装在车的哪个位置,朝向、高度、相对车身坐标系的偏移,最好配一张实拍照片或示意图,不要只写"装在前挡风玻璃上方"这种描述不清楚的话。
- **外参和摆放要对得上**:写清楚当前用的外参是哪次标定产出的、标定时间、用的哪个标定脚本/配置文件,换过摆放位置但没重新标定的,要在 README 里标红说明。
- **线材要求**:接口类型(USB-C / HDMI / 以太网供电等)、最短长度(比如"摄像头到工控机至少 3 米,买短了够不到"),特殊线材(高速数据线、工业相机专用线)从哪采购或者组里现成库存在哪,别让人到了车上才发现线不够长或者接口不对。
- **供电、支架这类"不是代码但没有就跑不了实验"的东西**,一并列出来,别漏掉。

## 八、一致性检查

README 里写的和代码里实际跑的,时间久了容易对不上——尤其传感器外参、坐标系定义这类数字,代码改了参数没人同步改 README,下一个人很可能照着错的假设去复现实验或者直接上车。

- 有条件的话写一个检查脚本(比如 `scripts/check_consistency.py`),把 README/配置文档里写的关键数字(传感器位置、外参、分辨率、采样率)和代码里实际用的配置做一次比对,接入 CI 跑,对不上就报错,而不是等装车才发现。
- 做不到自动化的,至少在 PR review 清单里加一条:"这次改动如果动了传感器配置/外参,README 里对应的描述是不是也一起改了"。
- 车辆实验尤其要注意:代码里的传感器坐标/外参,必须和 README 描述的物理摆放对得上。换一次车、挪一次摄像头位置,外参文件和 README 里的示意图/文字要一起更新,不能只改一边。

## 九、维护节奏

- 每个仓库有一个 manager,README 顶部的"维护人"写的就是他。
- main 每月合入一次:manager 在月度组会前那个周末整理好、提 PR,周一组会上 Owner 审核通过后合入。具体操作见 [MERGE_WORKFLOW.md](MERGE_WORKFLOW.md)。
- Google Sheet 继续用,但只当索引:每个仓库每月一行,写 manager、PR 链接、审核结果。具体改了什么写在 PR 和 README 里,不在 Sheet 里重复写。表头见 [templates/monthly_review_sheet.csv](../templates/monthly_review_sheet.csv)。
- 本月没东西合入也要在 Sheet 里填一行,写清原因。每个月都有记录,才看得出哪个仓库落灰了。
- README 顶部的"状态"字段(active / 交接中 / archived)和"已知问题"段落,每次月度合入时顺手更新。
- commit 不要攒着,平时小步提交。真要交接的时候发现一堆没写清楚、自己都忘了为什么这么改的代码,比随手花十分钟补一条 commit message 贵得多。

## 十、AI 协作时代,再加几条

现在不少人用 Claude Code 这类 AI 工具接手别人的项目,下面几条是为了让这件事顺畅,顺带也是对人更友好的标准,不是额外负担:

- 仓库放一个 CLAUDE.md(或者统一叫法),写给 AI 看的项目须知:关键目录是什么、哪些文件不能动、怎么跑测试、已知的坑。这些本来就是交接时该写清楚的隐性知识,写成 AI 能直接读的格式,人接手也一样受益——HANDOFF 类文档本质就是这个,只是要确保 AI 翻开仓库第一件事就能找到它,不用先把全部代码翻一遍去猜。
- requirements 里版本号钉死(`==`,不是 `>=`)。AI 帮你装环境或者升级依赖的时候,模糊版本容易被"顺手优化"掉,装出一个本机测不出问题、换机器全崩的环境。
- 给一个一键自检脚本(比如 `scripts/smoke_test.sh`),跑完告诉你环境对不对、路径通不通、模型能不能跑一次最小推理。不管接手的是人还是 AI,第一步都应该是跑这个脚本,而不是凭经验猜"装得对不对"——这比写一百字说明"怎么验证环境装好了"可靠,文字里的细节人会跳着看漏,AI 处理长文档时同样会漏。
- 前面说的并行/串行步骤、README 和代码的一致性检查,能写成脚本就不要只写在文字里。顺序和一致性这种事交给脚本去保证,不要指望每个读文档的人(或者 AI)都精确执行"终端 A 和终端 B 要同时开"这句话,也不要指望有人会手动去对传感器外参数字。
- AI 不会把一份烂文档变好,只会更快地把烂文档传给下一个人。组会上用 AI 帮忙"过一遍这几个仓库的状态"没问题,但前提还是每个仓库自己把 README、结果波动范围、硬件描述写诚实、写具体——这条标准对人和对 AI 是一回事。

## 十一、检查清单

发 PR 或者第一次把项目挪进组织仓库前,自己过一遍下面这几条。完整的逐项自查表(包括开源前的要求)见 [REPO_CHECKLIST.md](REPO_CHECKLIST.md)。

- [ ] 别人 clone 下来,跟着 README 能装上环境(GPU/驱动/CUDA 版本对得上)
- [ ] 跟着 README 的命令能跑出结果,不用来问你
- [ ] 没有数据集、权重、密钥、视频文件被提交进去(翻一下 git log,历史里有的话要清)
- [ ] requirements.txt / environment.yml 是最新的,版本钉死,不是半年前的
- [ ] README 顶部写了维护人和状态
- [ ] 代码里没有写死的本机绝对路径;写不掉的那几个在 README 里显式列出来了
- [ ] 多终端/多进程的步骤讲清楚了哪些要并行开、哪些要串行
- [ ] 关键结果的复现性写清楚了:能复现的给了命令和种子,不能完全复现的给了波动范围和原因
- [ ] 涉及实车/实体实验的,传感器摆放、外参来源、线材要求写清楚了,而且和代码里的配置对得上

就这些,核心就三句话:README 让人不用问你就能跑起来,换一台机器也一样,报的结果经得起复现。有问题在组会上提。
